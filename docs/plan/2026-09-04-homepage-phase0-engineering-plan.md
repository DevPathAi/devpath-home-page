## 한 줄 결정

`leva.ai.kr`는 이미 정식 홈페이지다. 따라서 구 랜딩을 별도 사이트로 유지하거나 새 홈페이지를 한 번에 다시 쓰지 않는다. 먼저 현재 홈페이지를 신청서·90초 영상·실제 앱과 일치시키고 구 랜딩의 데이터와 보안을 정리해 닫는다. 안정 배포 뒤 기존 URL을 그대로 보존한 채 Astro로 옮기고 상세 페이지를 순차 추가한다.

## Problem Statement

레바에는 새 홈페이지가 없는 것이 아니라, 이미 운영 중인 홈페이지와 구 검증 랜딩이 서로 다른 제품을 설명하는 문제가 있다.

- `https://leva.ai.kr/`는 현재 `devpath-home-page`가 서비스하고 있다. 즉 이번 작업은 도메인 교체가 아니라 콘텐츠·퍼널·서비스 자산 통합이다.
- 홈페이지 H1, 4단계 흐름, CTA, 메타데이터가 2026년 9월 신청서 및 90초 영상의 표현과 어긋난다.
- 홈페이지의 4번째 단계는 아직 `Q&A 커뮤니티`이고, 신청서 설계는 `경로 보정`을 말한다. 다만 현재 배포 UI에서 자동 경로 보정을 확인하지 못했으므로 그대로 교체하면 새 불일치가 생길 수 있다.
- `AI 멘토 초대 신청`이 mailto로 남아 있어 진단 → 결과 저장 → 대기자 등록/초대라는 단일 퍼널과 충돌한다.
- `devpath-landing-page.pages.dev`에는 과거 DevPath AI 5분 인터뷰 랜딩이 공개되어 있어 브랜드·제품 정의·전환 경로가 중복된다.
- `www.leva.ai.kr`와 `devpath-home-page.pages.dev`가 별도 200 응답을 내므로 canonical만으로는 해결되지 않는 중복 호스트가 있다.
- 구 랜딩에 연결된 AI/Turnstile/Apps Script 자격증명은 과거 운영 방식까지 포함해 회수·폐기 여부를 검증해야 한다.
- 수제 정적 페이지 구조는 지금까지는 충분했지만, 13개 페이지와 notes/updates/research 컬렉션을 반복 레이아웃·수동 sitemap 목록으로 관리하기에는 오류 비용이 커진다.

목표는 페이지 수를 늘리는 것이 아니다. 심사자와 잠재 사용자가 5분 안에 `사수 없는 0~3년차 개발자를 위한, 학습 활동에서 맥락을 만드는 AI 사수`라는 동일한 제품을 보고, 가입 없이 진단을 시작하게 만드는 것이다.

## Demand Evidence

현재 확보된 수요 근거는 과장 없이 다음처럼 구분한다.

- 자체 설문 자유응답에서 12건 중 7건이 “기존 범용 AI로 충분하지 않은가”라는 반론을 제시했다. 홈페이지는 이 반론을 피하지 않고 같은 질문의 Before/After 실화면으로 답한다.
- 유료 패널 97명과 자체 채널 18명 조사는 표본 성격이 달라 합산하지 않는다. 수치 공개는 `/research`에서 출처·기준일·표본을 분리할 수 있을 때만 한다.
- 1차 204건 데이터는 표본 타당성을 확인하지 못해 전량 폐기했다. 이 폐기 결정은 검증 규율의 근거이지 시장 수치로 재사용하지 않는다.
- 앱은 2026년 8월부터 `app.leva.ai.kr`에서 동작하며 게스트 진단, 로드맵, AI 멘토 세션을 실제 화면으로 확인할 수 있다. AI 멘토는 초대 기반 비공개 베타다.
- 1차 평가의 핵심 약점은 “구체적 서비스 흐름 부족으로 차별화 확인이 어렵다”였다. 홈페이지의 첫 과제는 더 많은 주장이 아니라 이미 구현된 흐름의 증거를 보여주는 것이다.

공개 수치의 기준은 “좋아 보이는 숫자”가 아니라 출처와 이벤트 정의를 재현할 수 있는가다. 진단 완료, 결과 저장, 초대 요청, 멘토 세션 시작 이벤트가 같은 정의로 계측되기 전에는 누적 숫자를 홈페이지에 올리지 않는다.

## Status Quo

### 사용자가 현재 겪는 흐름

1. 개발 중 막히면 범용 AI에 자신의 경력, 학습 주제, 진도, 직전 오류를 다시 설명한다.
2. 일반적인 답을 받은 뒤 자기 상황에 맞는 부분을 다시 골라야 한다.
3. `leva.ai.kr`에서 제품을 알아보더라도 신청서·영상과 다른 H1 및 `Q&A 커뮤니티` 흐름을 만나 차별화 판단이 흐려진다.
4. 게스트 진단 링크는 열리지만 AI 멘토 접근 방식은 mailto와 앱 초대 구조로 나뉜다.
5. 검색이나 Pages 기본 도메인으로 구 랜딩에 도착하면 과거 DevPath AI 인터뷰 제품을 현재 제품으로 오해할 수 있다.

### 운영자가 현재 겪는 흐름

- 공통 헤더·푸터·메타가 HTML과 템플릿에 반복된다.
- `build.mjs`의 `DEPLOY_ENTRIES`와 `scripts/notes.mjs`의 `STATIC_PAGES`를 수동 동기화해야 한다.
- 새 페이지마다 sitemap, 탐색, canonical, OG, 테스트 목록을 각각 갱신해야 한다.
- 홈의 리드 폼, 앱 안의 초대 신청, 구 랜딩의 인터뷰/리드 흐름이 서로 다른 저장소와 함수에 남아 있다.

## Target User & Narrowest Wedge

### 1차 사용자

사수 없이 새 스택을 배우거나 실무 오류를 해결해야 하는 0~3년차 개발자다. 이 사용자는 “AI가 더 똑똑한가”보다 “내가 무엇을 배우고 어디서 막혔는지 다시 설명하지 않아도 되는가”를 확인한다.

### 2차 사용자

신청서 URL을 열어 보는 심사자·멘토다. 이 사용자는 문서에 적힌 기능이 실제로 존재하는지, 접근 제한이 정직하게 안내되는지, 화면과 주장이 일치하는지를 5분 안에 본다.

### 가장 좁은 유효 범위

홈 한 장에서 다음 세 가지가 성립하면 Phase 0는 가치가 있다.

1. 같은 질문의 Before/After 실화면으로 차이를 이해한다.
2. 진단 → 로드맵 → AI 멘토 → 확인된 다음 행동의 흐름을 본다.
3. `가입 없이 진단 시작`을 눌러 공개 진단으로 이동한다. 멘토가 초대 기반이라는 사실은 CTA 바로 근처에서 확인한다.

B2B, 브랜드 다운로드, 연구 결과 공개는 이 세 가지를 흐리지 않는 후속 페이지다.

## Constraints

- 2026-09-16 제출 전에는 전면 재작성보다 안정적인 사실 정렬이 우선이다.
- 홈페이지·신청서·90초 영상은 제품 문장을 단어 단위로 맞춘다.
- 실화면에서 확인할 수 없는 기능은 현재 기능으로 말하지 않는다.
- Before/After 응답은 같은 질문에 대한 실제 원문이며, 응답 문장을 편집하거나 여러 테이크를 합성하지 않는다.
- AI 멘토는 초대 기반 비공개 베타다. `지금 바로 전 기능 사용`처럼 전면 개방으로 읽히는 CTA는 금지한다.
- 시장 규모, SOM, 검증되지 않은 효과, `한국 최초`, `유일`, `최고`를 사이트에 넣지 않는다.
- 숫자는 출처, 기준일, 이벤트 정의를 함께 제시할 수 있을 때만 공개한다.
- 기존 URL(`/about`, `/beta`, `/notes/`, `/privacy`, `/terms`)과 검색 자산을 보존한다.
- Release A에서는 `/api/lead`, `/api/stats`를 UI에서 분리한 채 롤백용으로만 보존하고, Release B에서 관련 Functions·클라이언트·테스트·Apps Script 설정을 제거한다. Astro 전환에는 이 레거시 API를 가져가지 않는다.
- 개인정보·리드 데이터를 삭제하기 전 내보내기와 보존 근거를 확인한다.
- 현재 체크아웃된 `feat/seo-note-cta`는 `origin/develop`보다 뒤처졌고 원격 추적 브랜치가 사라진 상태다. 구현은 최신 `origin/develop`에서 새 브랜치를 만들어 시작한다. 사용자 소유 변경은 리셋하거나 덮어쓰지 않는다.
- 구 DevPath의 블루/오렌지 디자인 토큰과 대학생·14,900원 포지셔닝은 재사용하지 않는다.

## Premises

1. 홈페이지의 역할은 제품 설명서가 아니라 실제 제품으로 들어가는 신뢰 가능한 관문이다.
2. 모든 공개 표면의 기준 문장은 신청서 Q1/Q11, 90초 영상 엔드카드, 실제 앱 접근 구조다.
3. 차별화는 “AI 멘토”라는 명칭보다 학습 활동에서 만들어진 맥락과 보내기 전 확인·수정 가능성에서 나온다.
4. 홈의 주인공은 추상 도식이 아니라 동일 질문 Before/After와 실제 앱 화면이다.
5. 게스트 진단은 공개하고, AI 멘토는 결과 저장 후 대기자 등록 및 순차 초대로 안내한다.
6. 구 랜딩의 AI 인터뷰 UI나 구 카피는 이식하지 않는다. 보존할 것은 연구·리드 기록과 운영 학습뿐이다.
7. AdSense 승인은 정보 구조의 목표가 아니다. 충분한 독자 콘텐츠와 일관된 탐색을 만든 결과로 다룬다.
8. 13개 페이지와 3개 콘텐츠 컬렉션은 Astro 도입을 정당화하지만, 마감 전 마이그레이션을 정당화하지는 않는다.
9. `경로 보정`은 제품 방향이지만 현재 공개 기능 문구는 화면 증거를 따라야 한다. 자동 보정 UI·트리거가 재현되지 않으면 Phase 0의 4단계는 `진행 확인` 또는 `완료 조건과 다음 단계`로 표기하고, 경로 보정은 `/beta`의 예정 기능으로 둔다.

## Approaches Considered

### Approach A: 제출 전 전면 리뉴얼과 Astro 동시 전환

홈, 상세 페이지, 콘텐츠 컬렉션, URL, 폼을 한 번에 Astro로 옮기고 즉시 새 정보 구조를 배포한다.

장점:

- 최종 구조에 가장 빨리 도달한다.
- 공통 레이아웃과 메타 자동화가 즉시 가능하다.

단점:

- 신청 마감 직전에 카피 수정, 프레임워크 전환, Functions 연결, SEO 이동, 시각 회귀가 한 릴리스에 섞인다.
- 장애 시 원인이 콘텐츠인지 라우팅인지 빌드인지 분리하기 어렵다.
- 실제 화면 확보보다 프레임워크 이전이 일정의 주인이 된다.

판정: 기각. 지금의 가장 큰 위험은 기술 부채가 아니라 공개 표면의 사실 불일치다.

### Approach B: 사실 정렬·구 랜딩 종료 후 URL 보존 Astro 전환

Phase 0에서 현재 정적 구조를 유지한 채 콘텐츠, 실화면, CTA, SEO, 구 랜딩 보안을 정리한다. 안정 배포 후 Phase 1에서 동일 URL·동일 동작을 먼저 Astro로 옮기고 새 페이지를 추가한다.

장점:

- 신청서, 영상, 앱, 홈페이지를 가장 빨리 일치시킨다.
- 각 릴리스의 실패 범위가 작고 이전 Cloudflare 배포로 즉시 롤백할 수 있다.
- Astro 전환 전후를 URL·스크린샷·응답 상태로 비교할 수 있다.
- 구 랜딩의 비용·보안·브랜드 위험을 프레임워크 작업과 독립적으로 닫는다.

단점:

- Phase 0에서 일부 정적 HTML을 한 번 수정한 뒤 Phase 1에서 다시 컴포넌트화한다.
- 짧은 기간 동안 기존 빌드 목록의 수동 관리가 계속된다.

판정: 채택. 이 중복 비용은 안정성과 사실 정확성을 사는 제한된 비용이다.

### Approach C: 두 사이트를 유지하고 상호 링크만 정리

`leva.ai.kr`은 소개 사이트, 구 Pages 랜딩은 인터뷰/리드 획득 도구로 계속 운영한다.

장점:

- 구 기능과 데이터 수집 흐름을 바로 폐기하지 않아도 된다.
- 코드 변경이 가장 적다.

단점:

- 서로 다른 제품명, 대상, 기능, CTA가 계속 검색되고 공유된다.
- 두 퍼널의 이벤트와 동의, 데이터 보관, 자격증명을 계속 운영해야 한다.
- 심사자에게 어느 사이트가 현재 사실인지 설명 비용이 생긴다.

판정: 기각. 구 인터뷰가 현재 핵심 제품이 아닌 이상 유지비가 학습 가치보다 크다.

### 승인된 홈 와이어프레임

1. Hero: Q11 훅, 제품 한 줄, 90초 실화면 영상, `가입 없이 진단 시작`, `작동 방식 보기`, 접근 제한 안내.

3. 4단계 흐름: 진단 → 로드맵 → AI 멘토 → 검증된 다음 행동. 마지막 단계 명칭은 경로 보정 사실 게이트를 통과해야 한다.
4. 무엇이 함께 가는가: 주제·진도·직전 오류, 보내기 전 확인·수정, 코드 원문·비밀값 미전송 원칙.
5. 최근: 변경 기록 3건과 개발 기록 3편.
6. 만드는 사람과 최종 CTA.

러프 와이어프레임은 `devpath-home-page/test-results/office-hours-home-wireframe.html`과 PNG에 있다. 이는 구현 UI가 아니라 정보 위계 확인용이다. 최종 화면에는 실제 앱 스틸과 90초 영상을 사용한다.

### Phase 0 — 일치와 종료 (제출 전, 프레임워크 유지)

#### P0-A. 안전한 구현 기준선

1. `origin/develop`을 갱신하고 그 커밋에서 새 작업 브랜치를 만든다.
2. 현재 사용자 변경과 `feat/seo-note-cta`의 고유 커밋을 목록화한다. 필요한 항목은 선택적으로 이식하되 리셋하지 않는다.
3. 현재 production URL, status code, title, canonical, JSON-LD, CTA 목적지, 스크린샷을 기준선으로 저장한다.
4. 신청서·영상·앱에서 콘텐츠 기준표를 추출해 테스트 fixture 또는 단일 콘텐츠 모듈로 고정한다.

완료 조건: 구현 시작 커밋과 production 기준선이 재현 가능하고 사용자 변경 손실이 없다.

#### P0-B. 실패하는 계약 테스트부터 추가

- 홈에 Q11 훅과 제품 정의가 정확히 존재한다.
- 현재 제품 흐름에 `DevPath AI`, `14,900원`, `Q&A 커뮤니티`, `StockPilot`, `LearnFlow`가 없다.
- 각 섹션의 primary CTA는 하나이며 `https://app.leva.ai.kr/diagnostic`와 페이지·위치별 UTM을 포함한다.
- 초대 기반 무료 베타 문구가 CTA와 같은 화면 범위에 있다.
- title, description, OG, canonical, JSON-LD의 이름과 설명이 콘텐츠 기준표와 일치한다.
- JSON-LD에 `Organization.alternateName = 레바`와 `SoftwareApplication`이 있다.
- privacy/terms/about/beta/notes의 기존 URL이 build output에 남는다.
- 실제 증거가 없을 때 `자동 경로 보정` 문구가 생성되지 않는다.

완료 조건: 변경 전 테스트가 문제를 잡고 변경 후 통과한다.

#### P0-C. 홈 콘텐츠와 증거 교체

1. H1, 한 줄 소개, CTA 및 접근 안내를 기준표로 교체한다.
2. 90초 영상 업로드 전에는 같은 질문 Before/After의 실제 스틸을 사용하고, 업로드 후 지연 로드 영상으로 교체한다.
3. 영상의 컷 3~9에서 확보한 실제 앱 화면을 홈 4단계에 재사용한다. 목업과 카드 안 중복 헤드라인은 제거한다.
4. 전송 범위 화면에는 `주제, 진도, 직전 오류`와 보내기 전 확인·수정만 설명한다. 화면이나 정책으로 확인되지 않은 미전송 항목은 단정하지 않는다.
5. 현재 공개 4단계는 `진행 확인과 다음 미션`으로 확정한다. 완료 상태·현재 미션·다음 미션의 실제 화면만 사용하고, `자동 경로 보정`과 조건부 잠금은 `/beta`의 예정 기능으로만 둔다.
6. mailto 초대 폼, `이전에 만든 것들` 잔재, 중복된 CTA를 제거한다.
7. Notes 글 하단에 제품 CTA와 관련 글 링크를 추가한다.
8. `/about`에 대표자·회사 정보는 공개 가능한 범위까지만 보강한다.

완료 조건: 무음·모바일에서도 제품과 접근 구조가 이해되고, 모든 제품 주장이 실제 화면 또는 정책 원본으로 추적된다.

#### P0-D. SEO·호스트 단일화

1. `www.leva.ai.kr/*`를 `https://leva.ai.kr/$path`로 301 리디렉션한다. query와 path suffix를 보존한다.
2. `devpath-home-page.pages.dev/*`도 같은 apex 경로로 301 처리하거나 Pages 기본 도메인 접근을 차단한다.
3. canonical, OG URL, sitemap은 apex만 생성한다.
4. sitemap의 lastmod를 실제 콘텐츠 수정일에서 생성한다. 일괄 오늘 날짜로 덮지 않는다.
5. Search Console과 네이버 서치어드바이저에서 apex 소유권, sitemap, 대표 URL을 확인한다.
6. www↔apex는 같은 도메인의 호스트 정리이므로 Google Change of Address 도구를 사용하지 않는다.

Cloudflare는 www→apex에 Bulk Redirect와 301, query/path 보존을 권장한다. Google은 이동 시 URL 매핑, 영구 리디렉션, sitemap, 장기 모니터링을 권장한다.

완료 조건: www와 Pages 기본 도메인의 임의 경로가 한 번의 301로 동일 apex 경로에 도착하고 리디렉션 체인이 없다.

#### P0-E. 구 랜딩 흡수와 안전 종료

1. `devpath-landing-page`의 공개 route, Functions/API, KV key, Apps Script/Sheet, Turnstile widget, AI provider 사용처를 읽기 전용으로 목록화한다.
2. 리드/인터뷰 기록을 스키마와 수집 기간, 동의 문구, 출처를 포함해 내보낸다. 내보내기 성공과 건수를 검증하기 전 원본을 삭제하지 않는다.
3. 현재 홈페이지에 이식할 것은 원문 연구 근거와 운영 학습뿐이다. AI 인터뷰 UI, DevPath 카피, 구 가격은 이식하지 않는다.
4. `devpath-landing-page.pages.dev/*`의 유효 경로를 관련 canonical URL로 301 매핑한다. 단일 페이지의 `#apply` fragment는 서버에 전달되지 않으므로 기존 공유 링크를 찾아 홈/진단 URL로 갱신한다.
5. 알려진 경로와 결정적으로 생성한 임의 경로가 단일 301로 이동하고 path·query가 보존되는지 검증한 뒤 최소 24시간 관찰한다.
6. 관찰 기간에 Functions 호출이 0건임을 확인한 후 Cloudflare 프로젝트의 direct access와 Functions 실행을 중단한다.
7. 마지막 단방향 gate에서 Anthropic key, Turnstile secret, Apps Script 접근 토큰 등 구 랜딩 전용 자격증명을 실제 provider/API에서 폐기 또는 회전하고, 이전 자격증명이 거부되는지 확인한다. 저장소·Cloudflare 설정에서 제거한 것만으로 완료 처리하지 않는다.
8. 개인정보 처리방침을 실제 AdSense·AI·기타 수탁 처리 범위와 맞추고, 저장소는 삭제하지 않은 채 archived/read-only 상태로 보존한다.

완료 조건: 구 랜딩 화면과 유료 API가 외부에서 실행되지 않고, 필요한 데이터는 검증된 형태로 보존되며, 전용 자격증명이 provider 측에서 더 이상 유효하지 않다.

### Phase 1 — URL 보존 Astro 전환과 핵심 상세 페이지 (9/17~10/15)

Astro는 새로운 디자인을 만들기 위한 것이 아니라 반복되는 정적 페이지 계약을 자동화하기 위해 도입한다.

1. 새 마이그레이션 브랜치에서 현재 production URL과 output을 fixture로 고정한다.
2. `BaseLayout`, Header, Footer, SEO/JSON-LD, CTA, screenshot/figure, FAQ를 공통 컴포넌트로 옮긴다.
3. 기존 HTML을 URL-for-URL로 이전한다. 이 단계에서는 카피와 레이아웃을 재설계하지 않는다.
4. notes Markdown을 Astro content collection으로 가져오고 schema, 정렬, 태그, related posts, RSS, sitemap을 자동화한다.
5. Cloudflare Pages 정적 출력과 기존 Functions 라우팅을 유지한다. `/functions`는 프로젝트 루트에 두고, 생성된 `dist/_routes.json`이 정적 페이지를 Functions invocation에서 제외하면서 `/api/*`만 포함하는지 검증한다. `_redirects`는 Functions가 처리하는 요청에는 적용되지 않으므로 두 경로의 책임을 섞지 않는다.
6. 이전 전후 URL별 status, canonical, DOM 핵심 문구, screenshot, structured data를 비교한다.
7. parity 배포가 안정된 뒤 `/how-it-works`를 10월 1일 이전에 먼저 공개한다.
8. 이어서 `/pricing`, `/lcs`, `/updates`, `/contact`를 추가한다. 각 페이지는 별도 작은 릴리스로 낸다.

완료 조건: 기존 URL·Functions·검색 자산의 회귀 없이 수동 deploy 목록과 반복 레이아웃이 제거되고, `/how-it-works`에서 로그인 없이 실제 4단계 흐름을 확인할 수 있다.

## Success Criteria

### Phase 0 출시 기준

- canonical 홈페이지의 현재 제품 흐름에 `DevPath AI`, `14,900원`, `Q&A 커뮤니티`, `StockPilot`, `LearnFlow`가 0건이다.

- 모든 primary CTA가 게스트 진단으로 가고 `utm_source=leva.ai.kr`, `utm_medium=cta`, `utm_content={page-or-section}`을 보존한다.
- 시크릿 세션에서 게스트 진단이 로그인 없이 열리고, 결과 저장 시점과 AI 멘토 초대 제한이 실제 앱 안내와 일치한다.
- `www.leva.ai.kr/*`, `devpath-home-page.pages.dev/*`, 구 랜딩 공개 URL이 의도한 apex URL로 301 이동하며 redirect chain과 loop가 없다.
- title, description, OG, canonical, sitemap, Organization/SoftwareApplication JSON-LD가 동일한 브랜드와 apex URL을 사용한다.
- 구 랜딩의 AI 인터뷰/API는 외부에서 실행되지 않고, 전용 자격증명은 provider 측에서 폐기/회전되었다.
- 화면 증거 없는 `자동 경로 보정`, 자동 실력 향상, 임의 수치가 0건이다.
- Vitest, Playwright, build, link/redirect, visual, 접근성 검사가 통과하고 320~1440px에서 치명적 레이아웃 오류가 없다.
- production console error와 실패한 필수 network request가 0건이다.

### Scope decision

- 구현 기준선은 네 저장소 모두 최신 `origin/develop`에서 만든 새 브랜치다. 현재 체크아웃된 뒤처진 브랜치와 사용자 소유 변경은 건드리지 않는다.

### Data and control flow

#### Analytics v2 consumer-first flow

```text
Release R0: consumer compatibility

Home(v2 contract, UTM emit OFF)      App(v1 + v2 reader)        GitOps schema v2
             |                              |                         |
             +-------- journeyId ---------->|                         |
                                            +-- accepts no UTM -------+
                                            +-- accepts valid tuple --+
                                            +-- strips URL params ----+
                                            +-- session attribution --+

Release RA: Home alignment

site.config.mjs
   +-- diagnosticUrl(content)
   |      utm_source=leva.ai.kr
   |      utm_medium=cta
   |      utm_content=<approved enum>
   +--> rendered dist CTA --click--> app /diagnostic
                                      |
                                      +-- validate all-or-none tuple
                                      +-- store in sessionStorage
                                      +-- remove journeyId + UTM from visible URL
                                      +-- diagnostic_started(v2, optional tuple)
                                      +-- downstream events join by journey_id
```

Attribution contract:

- `utm_source`: exact `leva.ai.kr`.
- `utm_medium`: exact `cta`.
- `utm_content`: one of `header`, `hero`, `comparison`, `pricing`, `final`, `beta`, `notes-index`, `note-footer`.
- 세 값은 all-or-none이다. 중복·부분 tuple·허용 밖 값·64자를 넘는 값은 저장하지 않는다.
- invalid attribution도 진단을 막지 않는다. 인식한 `journeyId`와 UTM key는 URL에서 제거하고, 관계없는 query와 fragment는 보존한다.
- v2는 `diagnostic_started`에만 optional UTM tuple을 허용한다. 이후 funnel 결합은 기존 opaque `journey_id`를 사용해 고카디널리티 문자열 확산을 막는다.
- session key는 versioned key를 사용하며 localStorage, cookie, diagnostic continuation payload에는 복제하지 않는다.

### Executable release plan

#### R0 — analytics v2 consumer compatibility

1. `origin/develop`에서 Home·Frontend·GitOps 새 브랜치를 만들고 각 SHA와 dirty state를 기록한다.
2. v1 파일을 수정하지 않고 `mission-spine.analytics.v2.json`을 Home과 Frontend에 같은 LF bytes로 추가한다.
3. v2에는 `diagnostic_started`의 optional `utm_source`, `utm_medium`, `utm_content`와 `requiredTogether` 규칙만 추가한다. language-native validator가 JSON과 정확히 일치하게 한다.
4. Frontend의 handoff capture를 확장해 no-UTM과 valid tuple을 모두 받고, invalid tuple은 drop하며 진단은 계속한다. sessionStorage 실패도 기능 실패로 승격하지 않는다.
5. GitOps `schema-v2.json`은 analytics version과 raw SHA-256을 요구한다. `schema-v1.json`과 과거 validator semantics는 보존한다.
6. Home은 v2 계약을 탑재하되 CTA에는 아직 UTM을 내보내지 않는다.

완료 조건: production 앱이 기존 URL과 v2 URL을 모두 수용하고, visible URL을 정리하며, v2 계약 hash가 Home·Frontend·GitOps에서 동일하다.

#### RA — homepage factual, CTA, SEO and evidence alignment

### Worktree parallelization strategy

| Step | Modules touched | Depends on |
|---|---|---|
| A. Frontend v2 consumer | `devpath-frontend/apps/web/lib/src/analytics`, frontend analytics tests | contract tuple frozen |
| B. Home v2 contract carrier and homepage build/content/media | `devpath-home-page/src/analytics`, build/scripts/templates/assets/tests/e2e | contract tuple frozen; UTM emission deploy waits for A |
| C. GitOps schema v2 and Home release control | `devpath-gitops/release-manifests`, release scripts/tests/workflows | A+B canonical v2 hash |
| D. Old landing inventory/export preparation | `devpath-landing-page`, retirement evidence staging | — |
| E. Retirement protected workflow | GitOps retirement manifests/scripts/workflows | C+D; RA stable 24h |
| F. Approved manual ads | Home templates/assets/tests | Google approval; RA stable |

Parallel lanes:

- Lane A: Frontend v2 consumer.
- Lane B: Home contract/build/content/media. 구현은 A와 병렬 가능하지만 production UTM emit은 A 배포 후다.
- Lane C: Old landing read-only inventory/export preparation.
- Lane D: GitOps schema v2 → Home-only workflow → retirement workflow. A+B의 contract hash와 C의 inventory가 준비된 뒤 순차 실행한다.
- Lane E: AdSense approved_manual. 외부 승인 뒤 독립 실행한다.

Execution order: A + B + C를 병렬 작업할 수 있다. A와 B의 동일 contract hash를 확정한 뒤 D를 병합하고 R0를 배포한다. 이후 RA, 24시간 안정 확인, RB 순서다. E는 승인 이후 별도다.

Conflict flags:

- Lane A와 B는 다른 저장소지만 analytics v2 JSON bytes가 정확히 같아야 한다. Git merge 충돌은 없지만 hash drift 위험이 있으므로 D의 parity gate 전에는 배포하지 않는다.
- Lane B와 E는 모두 Home templates/tests를 건드린다. E는 RA 이후 새 브랜치에서 순차 진행한다.
- Lane D의 schema v2와 Home-only/retirement workflow는 같은 GitOps validator 계층을 공유하므로 한 lane에서 순차 구현한다.
