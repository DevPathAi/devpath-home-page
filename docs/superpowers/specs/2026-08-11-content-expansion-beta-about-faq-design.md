# 설계 — 홈페이지 콘텐츠 확장 (`/beta` · `/about` · 홈 FAQ)

## 1. 배경

애드센스 심사가 「준비 중」 상태이고, 리드 폼으로 들어오는 신청은 있으나 **베타가 무엇인지 설명하는 자리가 사이트 어디에도 없다**. "진단 시작 / 베타 초대받기"라고 적힌 폼 앞에서, 방문자는 초대되면 무엇을 받는지·언제 오는지·돈이 드는지를 알 수 없다.

실측한 현황(공백 제외):

| 페이지 | 본문 분량 |
|---|---|
| `index.html` (8섹션) | 1,624자 |
| `privacy.html` | 1,667자 |
| `/notes/` 6편 | 합계 약 9,200자 |

`/notes`가 심사용 콘텐츠의 대부분을 담당하고 있고, 홈은 섹션마다 카피가 한두 문단이라 짧다.

## 2. 목적

두 가지를 동시에 노린다.

1. **애드센스 심사** — 로그인 없이 읽을 수 있는 고유 페이지를 늘린다
2. **리드 전환** — 이메일을 넣기 직전의 불확실성을 없앤다

두 목적은 충돌하지 않는다. 읽을 값이 있는 설명이 신뢰를 만들고, 그 신뢰가 신청으로 이어진다.

## 3. 범위

**대상:** `devpath-home-page` 레포 하나.

**범위 밖:**
- **앱(`app.leva.ai.kr`)** — 다른 레포(`devpath-frontend`)이고 별도 사이클로 다룬다. 실측 결과 `<body>` 텍스트가 0자라 심사·SEO에 기여할 수 없고, 앱에 도달한 사용자는 이미 신청을 마친 사람이라 전환에도 기여하지 않는다.
- **이용약관** — 결제 기능이 없어 지금은 만들지 않는다. 개인정보 처리방침은 이미 있다.
- `/notes` 신규 원고 — 이 스펙 다음 사이클(콘텐츠 축 확장)에서 이어간다.

## 4. 만들 것

### 4.1 `/beta` — 베타 안내 (신규 `beta.html`)

신청 직전에 사람이 묻는 순서대로 답한다.

1. **베타가 무엇인가** — 지금 어떤 상태이고 무엇을 검증하는 기간인가
2. **무엇을 쓸 수 있나** — 적응형 진단 + 맞춤 로드맵 / AI 멘토(LCS) / 커뮤니티 Q&A. 각각 한 문단
3. **비용** — **베타 기간 전체 무료**
4. **초대 방식** — **신청 순서대로 순차 승인**
5. **아직 없는 것** — 준비 중인 것을 정직하게 적는다
6. **우리가 바라는 것** — 피드백
7. **신청 폼** — 홈과 같은 위젯

5번이 이 페이지의 핵심이다. 없는 것을 적는 쪽이 있는 것만 적는 쪽보다 신뢰를 만든다. `/notes`의 톤과 같다.

**5번에 쓸 항목은 구현 전에 확정한다.** 지금 사이트에서 확인되는 확정 사실은 **유료 플랜이 준비 중이며 베타 기간에는 과금이 없다**는 것 하나뿐이다(홈 요금 섹션). 그 밖에 "아직 없는 것"으로 적을 항목은 운영 사실이라 코드에서 알 수 없으므로, **구현 첫 단계에서 사용자에게 확인**한다. 확인되지 않으면 그 항목은 쓰지 않는다 — 추측으로 채우면 이 페이지의 목적 자체가 무너진다.

### 4.2 `/about` — 만드는 사람과 회사 (신규 `about.html`)

1. **왜 만드는가** — 홈 창업자 섹션(3문단)을 옮겨와 확장
2. **어떻게 만드는가** — AI와 협업해 만든다는 사실을 숨기지 않는다. `/notes`로 연결
3. **지금 어디까지 왔나** — 베타 진행 중
4. **회사 정보** — 상호·사업자등록번호·연락처
5. **연락** — `info@leva.ai.kr`

홈의 창업자 섹션은 **요약 3문단을 유지**하고 "더 읽기 → `/about`"으로 연결한다. 홈에서 통째로 들어내지 않는다 — 스크롤리텔링 위젯이 붙어 있고, 홈만 보는 방문자에게도 이 이야기가 필요하다.

### 4.3 홈 FAQ 섹션

`#pricing`과 `#lead` 사이에 신설한다. 요금을 본 직후이자 폼에 닿기 직전이 질문이 가장 많이 생기는 자리다.

항목(전부 확정 사실):

- 베타는 무료인가요?
- 초대는 어떻게 되나요?
- 무엇을 쓸 수 있나요?
- 진단은 얼마나 걸리나요?
- 개인정보는 어떻게 다루나요? (→ `/privacy`)
- 지금 서비스는 어떤 상태인가요?

각 답의 끝에서 `/beta`로 연결한다.

### 4.4 내비게이션

헤더·푸터에 `/beta`, `/about`을 더한다. `/notes`와 같은 방식이다.

### 4.5 `robots.txt`에 광고 크롤러를 명시

Google 문서상 **`Mediapartners-Google`은 `User-agent: *` 그룹을 무시**하고 자기 이름으로 쓴 규칙만 따른다. 현재 `robots.txt`에는 `*` 그룹밖에 없다. 명시 그룹이 없다고 차단되는 것은 아니지만, 심사 중인 지금 명시적으로 허용해 두는 편이 안전하다.

```text
User-agent: Mediapartners-Google
Allow: /
```

## 5. 콘텐츠 원칙

- **확정된 사실만 쓴다.** 초대 소요 기간처럼 정해지지 않은 것은 약속하지 않는다("순서대로 순차 승인"까지만 쓴다)
- **원고는 사람이 쓴다.** 서브에이전트에 맡기면 조사 맥락이 없어 일반론이 되고, 그건 심사가 정확히 거르는 것이다
- **없는 것을 적는다.** 준비 중인 기능을 감추지 않는다

### 5.1 공개 범위

| 정보 | 현재 상태 | `/about` | `/notes` 원고 |
|---|---|---|---|
| 상호 `레바` | 푸터·처리방침에 게시 중 | **게시** | 무관 |
| 사업자등록번호 | 푸터·처리방침에 게시 중 | **게시** | **금지** |
| 성명 `김민구` | **처리방침에 게시 중** (`privacy.html`의 개인정보 보호책임자 — 법정 기재사항) | **구현 시 확인** | **금지** |
| 사업장 주소 | 미게시 | **미게시** — 결제 기능이 없어 표시의무가 없다 | **금지** |
| CF Account/Zone ID·API 토큰, Apps Script `/exec` URL, 스프레드시트 ID, 내부 호스트명 | — | **금지** | **금지** |

정적 페이지와 원고의 금지 목록이 다르다. 사업자등록번호와 성명은 이미 의도적으로 게시돼 있으므로, 원고용 가드(`notes-content.test.js`)를 정적 페이지에 그대로 적용하면 안 된다.

`/about`의 창업자 이야기에 **실명을 쓸지는 구현 시 사용자에게 확인**한다. 처리방침에 이미 있으므로 새로 노출하는 정보는 아니지만, 창업자 서사에 이름을 붙이는 것은 별개의 선택이다.

## 6. 기술 구조

### 6.1 페이지 형식

`/beta`·`/about`은 **정적 HTML**로 만든다(`privacy.html` 패턴). `/notes`의 마크다운 파이프라인은 글(article)용이라 날짜와 `Article` 스키마가 붙는데, 안내 페이지에는 맞지 않는다.

### 6.2 URL

확장자 없는 clean URL: `/beta`, `/about`.

**트레일링 슬래시는 붙이지 않는다.** 실측상 Cloudflare Pages는 파일 기반 경로(`/privacy`)는 그대로 200을 주고, 디렉터리 인덱스(`/notes`)만 `/notes/`로 308 리다이렉트한다. `beta.html`·`about.html`은 파일이므로 `/privacy`와 같다.

canonical·`og:url`·sitemap·내부 링크 모두 슬래시 없는 형태로 통일한다.

### 6.3 리드 폼 재사용

위젯은 `document.querySelectorAll('[data-widget]')`로 마운트되므로 페이지와 무관하다. `beta.html`에 `<div data-widget="lead-form">`을 두고 `main.js`를 로드하면 홈과 같은 폼이 동작한다. `mail_sent` 기반 성공 문구도 그대로 적용된다.

### 6.4 애드센스

기존과 동일한 스크립트만 넣는다. **광고 슬롯(`<ins class="adsbygoogle">`)은 어디에도 넣지 않는다.**

### 6.5 ★정적 페이지 3자 일치 가드★

정적 페이지를 추가하면 **두 곳을 수동으로 갱신**해야 한다:

- `build.mjs`의 `DEPLOY_ENTRIES` — 빠뜨리면 파일은 있는데 **배포에서 조용히 제외**된다
- `scripts/notes.mjs`의 `STATIC_PAGES` — 빠뜨리면 sitemap에 실리지 않는다

`/notes`에서는 이 함정을 구조적으로 없앴지만(원고 집합에서 sitemap을 생성), 정적 페이지에는 그대로 남아 있다. 그래서 **테스트로 강제한다**:

> 루트의 `*.html` 집합(`404.html` 제외) == `DEPLOY_ENTRIES`의 html 항목 == sitemap 고정 경로 집합

셋 중 하나라도 어긋나면 실패한다. 앞으로 페이지를 추가할 때도 이 가드가 잡는다.

`404.html`을 제외하는 이유는 `noindex`라서 sitemap에 실리면 안 되기 때문이다. 가드는 이 예외를 명시적으로 다룬다.

## 7. 테스트

전부 TDD로 만든다. 확인 명령은 `npx vitest run`. **기존 141건을 깨지 않는다.**

| 대상 | 단언 |
|---|---|
| 3자 일치 가드 | 루트 html == DEPLOY_ENTRIES == sitemap 고정 경로 (404 제외) |
| 신규 페이지 head | canonical이 자기 URL(슬래시·확장자 없음) · `og:url` 일치 · `robots: index, follow` |
| 애드센스 | 스크립트 포함 · `adsbygoogle"` 슬롯 **부재** |
| `/beta` 폼 | `data-widget="lead-form"` 과 `main.js` 로드 |
| 홈 FAQ | FAQ 섹션 존재 · `/beta` 링크 존재 |
| 내비 | 헤더·푸터에 `/beta`·`/about` (기존 `content-compliance` 정확 일치 단언을 깨지 않는다) |
| 정적 페이지 금지 정보 | 대표자명·CF ID·Apps Script URL·시트 ID 부재 (**사업자등록번호는 허용**) |
| robots.txt | `Mediapartners-Google` 그룹 존재 |

## 8. 검증

1. `npx vitest run` 전건 통과
2. `npm run build` 후 `dist/`에 `beta.html`·`about.html` 존재, `sitemap.xml`의 `<loc>`가 **11개**(고정 5 = `/`·`/privacy`·`/notes/`·`/beta`·`/about`, 글 6). 현재는 9개다
3. 로컬 프리뷰로 **육안 확인** — 테스트가 green이어도 레이아웃 결함은 눈으로만 잡힌 전례가 여러 번 있다
4. 배포 후 **라이브 반복 측정** — 엣지가 경로별로 옛/새를 섞어 응답한다. 단발 측정으로 판단하지 않고, 연속 두 라운드가 같은 값을 낼 때까지 잰다
5. Search Console에 sitemap 재제출은 불필요(같은 URL, 내용만 갱신)

## 9. 위험

| 위험 | 대응 |
|---|---|
| 새 페이지가 배포 화이트리스트에 누락 | 3자 일치 가드(§6.5) |
| sitemap 누락 | 같은 가드 |
| 홈이 길어져 리드 폼 도달률 하락 | FAQ는 간결하게. 상세는 `/beta`로 보낸다 |
| 확정되지 않은 것을 약속 | §5 원칙. 초대 기간은 쓰지 않는다 |
| 심사가 원하는 건 분량이 아니라 고유성 | 기능 나열이 아니라 실제 운영 사실을 쓴다 |
